# Central release and publication notices

**Reported:** Diego's accepted 2026-10-23 instruction, after reviewing the pause
checkpoint and asking whether every component already knows the reporting rule.
**Status:** Resolved suite instruction delivery; MolI adoption remains separately owned by uibcdf/moli#75.

## What

Every new component release, with or without a package, and every new package
version/build/route needs a central issue notice. Suite members notify
uibcdf/molsyssuite; other MolI components notify uibcdf/moli through its own
adoption in uibcdf/moli#75. Existing source-release notices receive later artifact
events for the same component/version, preserving each original identity.

## How

The normative policy, issue template, root action, canonical guide and starter
define event timing, immutable evidence, unpublished/pending state and ecosystem
follow-up. Use the registered guide synchronizer and isolated documentary
deliveries with advance notices to existing member review homes. Preserve active
primary work. Verify local governance/index/guide routes and the exact published
administrative checkpoints; do not dispatch scientific suites for prose.

## Why

The audit read published root AGENTS.md files for sixteen suite members and five
direct MolI components. They route plausible shared-provider impact and public
release titles, but lack a universal event notice. Conditional impact reporting
does not ensure source-only releases or later package builds reach ecosystem
coordination. The original rule remains complementary, with advance notice due.

## What is measured and what is assumed

Read-only source/issue/instruction inspection establishes the gap and known
inventory. Instruction delivery is separate from future release compliance,
runtime compatibility and public-package qualification. Existing scientific/Qt
deferrals and other central work remain paused; this one policy
follow-up is specifically authorized.

## Alternatives and refuted paths

- Conditional impact notices alone miss otherwise unannounced release events.
- Automatic consumer/tag/package updates would conflate reporting with adoption.
- A new issue for each later file of one release would fragment one event record.
- Editing canonical consumer guide copies manually bypasses registered ownership.

## Scope and exclusions

All sixteen suite members, canonical/root/starter instructions and event template.
MolI owns its five direct-component adoption; #75 is the explicit handoff, not a
claim that the suite team changed their files. No release, tag, package, consumer
dependency/pin or scientific assertion is changed by this delivery.

## Acceptance criteria

- Publish the accepted policy and applicable exception/visibility route.
- Deliver explicit root AGENTS.md actions and byte-identical canonical-guide
  copies to all sixteen suite members through the registered synchronizer.
- Include future members through the versioned starter and onboarding guidance.
- Retain immutable documentary changes, owner notices and exact administrative
  checks, separately from release/publication event compliance.
- Cross-link the MolI-owned adoption without absorbing its delivery criteria.

## Local implementation issues

Use registered member review homes for the bounded instruction/guide delivery;
their historical closure is not a new runtime or release-compliance assertion.
The delivery receipt records the exact issue/notice for each member.

## Dependencies and risks

No central release preapproval is introduced. A tracker/credential limitation
requires an owned reporting handoff or bounded exception. Private evidence stays
private. Concurrent owner advances must be preserved by reapplying only the
documentary patch; never force a push or overwrite primary worktrees.
